# Albedo 用例册（当前真相）

本目录是**用户可见契约的唯一清单**。给人读、给人 review；可执行测试是它的影子，不是反过来。

这儿只放“用户能看见什么”，不放为什么、也不放实现。为什么与坑按主题放在
[`docs/notes/`](../notes/index.md)，改代码要守的规矩在 [`AGENTS.md`](../../AGENTS.md)。

## 编号规则

- 每条 `#### Scenario:` 带稳定 ID，形如 `SVG-001`，按能力前缀分组（见下表）。
- **ID 是稳定句柄，不是阅读顺序**：册子按语义分节，新场景先选节、再取下一个号。
  同一 Requirement 内按 ID 升序排列，跨 Requirement 不保证全局递增。
- **ID 一旦发布不复用、不重排。** 删除一条 = 显式评审动作，必须在改动说明里写清为什么这条契约不再成立。
- 编号固定三位，上限 999；要越过这个号段就说明该拆能力，而不是把号写长。
- **一条 Scenario 正文不超过 5 行**。写不下就把“为什么”与细节挪进 `docs/notes/`，不要挤在册子里。
- 一个能力超过 45 条时 `spec:check` 只提醒、不拦；拆不拆由人按“一次能不能读完并判断”决定。

## 写法规矩

1. **只写用户可观察的结果**：看得见的文字、几何、元素类型、文件里的结构。
   - ✗ “调用 `buildSourceSvg()` 时 patch 了源树”
   - ✓ “导入 3 个 `<rect>` 再导出，仍是 3 个 `<rect>`”
2. **不写实现**：不出现类名、函数名、局部变量名；实现换了，册子不该跟着换。
3. **一条 Scenario 只锁一个不变量**：可以有多条 WHEN/THEN，但只判断一件事。
4. **bug 回归先补 Scenario**：先把“现象”写成用户能复现的一条，再补失败用例，再改代码。
5. **结构性契约优先于字节级一致**：元素类型、数量、坐标、命令类型和未改动标记是契约；
   根节点尺寸、标题、必要的坐标包装可以规范化，不承诺整份文件逐字节相同。

## 与测试的绑定

可执行侧在测试标题开头挂册子号：

```js
test('[SVG-001] importing three rects exports three rects', async ({ page }) => { ... });
```

`npm run spec:check` 做两件事：

- 册子结构检查：ID 唯一、同一 Requirement 内升序、每条都有 `WHEN`/`THEN`、正文不超 5 行、
  别处引用的册子号真的存在。
- 双向覆盖检查：册子里有号但没有任何测试 = 未实现；测试有号但册子里没有 = 私测（禁止）。

测试可以一题多断言作为上下文，但标题里的那个号只对应一条 Scenario；
真正的契约由那条 Scenario 定义，而不是由测试名定义。
